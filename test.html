Trust through precision

Scrutiny is a feature.

Remote is designed to reduce blast radius, not to manufacture a false air gap. These are the boundaries operators should understand before placing valuable code or credentials inside a project.

Current boundary

Isolation

Projects use unprivileged LXD/LXC containers with separate filesystems, processes, mounts, and durable state. Containers share the host kernel and are not equivalent to hardened hostile multi-tenant VMs.

Agent-readable

Secrets lifecycle

Project secrets are authority deliberately given to the agent. They enter process environments and /workspace/.env; they are not hidden from the model or protected by application-level encryption at rest today.

Hardening gap

Network and resources

CPU, memory, and process limits use LXD/cgroups. The shared LXD bridge currently lacks project-to-project network policy, and host-backed workspaces/provider homes do not have default storage quotas.

Operator-owned

Backup and recovery

Durable state survives routine container replacement. Persistence is not backup: recovery from destructive in-project writes depends on Git remotes, snapshots, or backups maintained by the operator.

Trusted role

Host administrator access

The host administrator controls LXD, mounted project data, platform storage, routing, and provider authentication. Remote does not protect a project from a malicious or compromised host administrator.

Published openly

Known limitations

IDE membership parity, lateral bridge policy, secret hardening, mount quotas, built-in backups, and comprehensive audit coverage remain documented hardening work—not invisible footnotes.

Straight answers

What operators should know.

The short version: Remote gives agents a capable computer, keeps the control plane outside it, and documents where today’s boundary ends.

What exactly is a Remote project?

A project is a durable body of work backed by an unprivileged Linux container. It has its own workspace, chats, processes, ports, browser profile, project secrets, settings, and provider homes. Think of it as a server-side computer dedicated to one project.

Is Remote another AI agent?

No. Remote is the self-hosted project computer and control plane where Codex, Claude Code, Kimi, and future agents can work. The model is replaceable; the project home remains.

Does “isolated” mean a separate virtual machine or an air gap?

No. Projects use unprivileged LXD/LXC containers that separate filesystems, processes, mounts, and project state, but they share the host kernel. The current shared bridge also needs stronger project-to-project network policy. Read the threat model before treating Remote as a hostile multi-tenant boundary.

Can the host administrator access a project?

Yes. The host administrator is a trusted role with control over LXD, mounted project data, platform storage, routing, and provider authentication. Remote contains project processes from ordinary host access paths; it does not defend against a malicious or compromised administrator.

Can an agent read project secrets?

Yes. Secrets granted to a project are agent-readable authority. They are provided through execution environments and /workspace/.env. Scope them as if you were giving them to a capable root process inside that project computer.

Are durable project files automatically backed up?

No. Durable mounts survive routine container replacement, but persistence is not backup. Use Git remotes and operator-managed snapshots or backups for recovery from accidental or malicious in-project deletion.

What server do I need?

Start with a fresh Ubuntu or Debian host, root or sudo access, working key-based SSH, a domain with the documented base and wildcard records, and ports 80 and 443 open. Capacity depends on how many projects, agents, browsers, and builds you run concurrently.
